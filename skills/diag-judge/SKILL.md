# diag-judge —— 判「这次诊断做得对不对」，并挖出 dbdog 该修什么

这是诊断飞轮的第三棒。第二棒 `diag-run` 把复现跑成 trace；你这一棒判它，
产出是两样：**这次判成什么**，以及**dbdog 要修的条目**。

后者才是这条 loop 的 KPI。它的价值是「作为找 bug 的工具产出了多少 dbdog 的问题」，
不是被测 agent 的命中率——低命中率本身不是坏事，它是「这里有问题」的指示灯。

## 判据是差集，不是队列

跟 `diag-run` 不一样，这一棒**不抢队列**。因为诊断不只从批跑来：用户自己在 Claude Code 里
发一句「诊断: …」也会产出 trace，那种 trace 根本没有诊断表的行，但它同样该判。

所以待判集合是「跑过但没判过」现算的差集。诊断表那边**有行就把状态推到「待修」，
没有就跳过**——表是给人看进度的，不是判题的准入条件。

## 开跑前确认

`DBDOG_BASE_URL`、`DBDOG_API_KEY`、`DBDOG_MCP_URL`、`DBDOG_MCP_BEARER` 四样，
缺了问用户要，写进 `~/.claude/settings.json` 的 `env` 块。

**判题会话必须挂 MCP**，这是硬要求不是优化：判「要不要修 dbdog」的唯一硬判据是
**拿这次诊断的实例与时间窗去实际查一遍**——模型说没有的那条证据，究竟是它没想到查，
还是查了也确实没有。只看轨迹猜，这一项判不出来。

这一棒**不需要**禁读根：判题方本来就该看见答案，它的活就是拿答案对轨迹。

## 跑

```bash
S=<本 skill 同级的 diag-flywheel/scripts 目录>
node $S/llmobs/loop-judge.mjs --dataset <用例集名> --timeout-sec 1800 [--limit N]
```

一例一个会话，不是一轮一个。早前按轮导过，三例材料叠起来 11 MB 塞进一个会话，
40 分钟没判完，而且一例失败整轮都不回流。

## 看输出

- `诊断表里待判题 N 条` —— 有表行的那批。
- `⚠ N 例没有探针结果` —— **这条要留意**。探针是判「可信」的唯一硬证据；没有它，
  「可信」只能按「没抓到撒谎」判，结论偏软。缺探针的用例要回头补反向证据链。
- `本轮判题：成 X 例 · 败 Y 例`

跑完告诉用户：判了几例、判成什么、**挖出几条待修**。最后一项是这条 loop 存在的理由，
别把它埋在日志里。

## 判完之后

待修条目在控制台的用例表「判题」列点开看，按「改哪里」聚合，每条指到具体 span。
一条待修的两个关键字段是 `key`（跨轮认「同一个缺口」的稳定短名）和
`fix_where`（能直接打开的那个位置，只写一处——五处改动就是五条）。

## 定时

不要自己装 launchd / cron。用 `/loop 30m /diag-judge`。

跟 `diag-run` 错开跑：诊断在跑的时候判题捞不到东西，白起一个会话。
