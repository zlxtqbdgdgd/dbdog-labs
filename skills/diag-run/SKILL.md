# diag-run —— 领一批待诊断的复现，跑成 trace

诊断飞轮的第二棒。第一棒是**复现**（dbdog-benchmark 做，跑完把时间窗推给 dbdog，
一次复现在诊断表里落一行）；你这一棒把复现变成 trace；第三棒 `judge-run` 判它。

## 口令

**「dbdog test loop N」= 这一轮跑 N 条**：领最多 N 条待诊断的复现跑完。
N 缺省是 5。用户说「dbdog test loop 3」就是 `--max-per-round 3`。

**只管诊断，不接着判。** 判题是 `judge-run` 的活，它在**另一个会话**里由 `/loop` 单独驱动
（owner 2026-09-11 定）。两条 loop 各跑各的节奏，谁挂了都不拖累另一条——
串成一趟会让诊断的进度依赖判题活着。

要反复跑就 `/loop 30m /diag-run`——**不要自己装 launchd / cron**，那要改用户机器的开机项，
还得按平台分两套，而且它会自己起来烧 token。

## 为什么是「领」不是「算」

此前待跑集合是每轮现算的差集「有复现、没 trace」。**那个算法没有在途这一档**：
一轮间隔 30 分钟而单条诊断可能跑 40 分钟，两轮必然重叠——第一轮还在跑，第二轮去算差集，
那条还没有 trace，于是被当成待跑又发一遍。同一次复现诊断两遍，烧两份预算，
还在判题队列里留下两条互相矛盾的轨迹。

改成抢诊断表之后，抢的动作在服务端是单条带行锁的 UPDATE，抢到即占住租约，别人看不见。

## 开跑前确认这几样

缺任何一样都**不要跑**——宁可这一轮不跑，也不要跑出一轮盲测失效的数据。
缺了就问用户要，拿到后写进 `~/.claude/settings.json` 的 `env` 块（那是 key 的单一来源）。

| 变量 | 是什么 |
|---|---|
| `DBDOG_BASE_URL` | dbdog server 地址 |
| `DBDOG_OPERATOR` | **跑这一轮的人是谁**（如 `qinqiang`）。没有就问用户要，别自己编——见下 |
| `DBDOG_API_KEY` | 控制台 `/settings/api-keys` 签发；已配 `DBDOG_OBS_API_KEY` 就复用那个值 |
| `DBDOG_MCP_URL` | 诊断会话连的 MCP 地址，带 toolsets/skillsets 查询串 |
| `DBDOG_MCP_BEARER` | 连 MCP 的 bearer。**用 bearer 不走 OAuth，所以远端 http 地址可以直连**，不用回环反代 |
| `DIAG_WORKDIR` | **被诊断的那棵源码树**，会话的 cwd，要对得上被复现的那个版本 |
| `CLAUDE_CONFIG_DIR` | **考生跑在哪份配置下**（决定被测模型与端点）。没有就问用户要，别自己挑一份——它随机器和项目阶段漂 |
| `DENY_ROOT`（可多个） | **禁读根**，见下 |

### trace 是**跑完当场**写回诊断行的，不等整轮结束

每条诊断跑完、实验事件一落，`run-experiment` 就把 trace 写回它那一行并推到「待判题」
（loop 用 `--diagnosis rec=diagId` 把对应关系交给它）。这样两件事才成立：控制台里那次运行
与那一行复现当场认得上亲（否则一轮 40 分钟里同一次复现显成两行）；**轮次被 Ctrl-C 掐掉也不丢**
——2026-09-11 实测过丢的样子：19 行诊断 trace 全空，跑过的那些从此没人认领。

收尾那段推进还留着，是兜底：一条 trace 都没跑出来时要放回待诊断（那是它独有的活），
以及当场回填没打通时再补一次。

### `DBDOG_OPERATOR` 是谁在跑，问用户要

它落进诊断表的 `status_changed_by`，控制台用例表「状态」列底下那行显的就是这个串。
**缺了 loop 会当场拒跑**，而且是在抢任何一条待办**之前**就拒——抢到手的行会被占住租约，
跑到推状态那一步才发现缺变量，那批行得等租约超时才捞得回来。

别拿别的东西顶：`--claimed-by` 那个 `loop-diagnose@主机名` 记的是**哪条 loop 占着租约**
（卡住时去哪台机器看），`$USER` 在共用机器上人人都是 `dbdog`。这一列是拿去问
「这步谁推的」的，一个看着像答案的假答案比报错更坏。

### 禁读根是什么，为什么不能省

评测跑的是**盲**诊断：agent 只该靠遥测与源码推出根因。但答案往往就在同一台机器上——
社区 issue 原文、历史轮次报告、ground truth 文件。不挡住的话它 grep 一次就抄到了，
**而且没有任何迹象**：跑批照跑、分数照涨。2026-08-16 实测漏过一次，agent 第三步就
`ls` 到了语料库的兄弟目录，通道是开的，它只是自述「按盲测规则不读」。

所以要问用户：**哪些目录放着这道题的答案**。典型是语料库/issue 镜像、历史报告目录、
整个产品源码仓。宁可多圈几个——圈错了最多让 agent 少看一点，圈漏了整轮评测作废。

护栏两层，脚本自动装，不用你操心：`permissions.deny` 挡工具面（每个根三条，
Read/Grep/Glob 各有自己的 path 参数），PreToolUse 钩子挡 Bash 的 `cat`/`grep`/`head`
——那条路 deny 一个字节都不挡。

## 跑

```bash
S=<diag-flywheel/scripts 目录>   # 你知道自己的 skill 装在哪
node $S/llmobs/loop-diagnose.mjs \
  --dataset <用例集名> \
  --workdir "$DIAG_WORKDIR" \
  --deny-root "$DENY_ROOT_1" [--deny-root "$DENY_ROOT_2" ...] \
  --timeout-sec 2400 \
  --max-per-round <N>
```

跑完就完，**不要接着判**——判题在另一个会话里由 `/loop /judge-run` 驱动。

⚠️ **两条 loop 别同时跑**：本机多个 headless claude 进程并发会抢登录态（判题也是 claude 进程）。
两个会话各自 `/loop 30m` 的话，把起跑时刻错开——比如诊断整点跑、判题半点跑。

## 开跑第一行会印被测模型，**看一眼再走开**

```
被测模型=<解开后的真模型名>（来源 env，端点 <网关 host>）
```

不传 `--model` 时，headless 会话走的是 `ANTHROPIC_MODEL` / `ANTHROPIC_BASE_URL` 两个环境
变量（多半从 `~/.claude/settings.json` 的 `env` 块继承）。**换台机器、或者哪天改了那两行，
被测模型就悄悄换了**，而跑批照跑、分数照记。所以开跑时印出来，也一并记进 run metadata。

### 本项目的分工（owner 2026-09-11 定）

| 角色 | 该用哪一档 | 从哪来 |
|---|---|---|
| **被诊断的 agent**（本 skill 起的会话） | 便宜快的那一档 | 考生那份 `CLAUDE_CONFIG_DIR` 的 `env` 块 |
| **判官**（`judge-run` 起的会话） | 强的那一档 | 判官那份 `CLAUDE_CONFIG_DIR`，见 `judge-run` |

**考生用便宜快的、判官用强的**：诊断要跑很多轮、很长，成本在这儿；判卷判错了整条 loop
的产出都不可信。

**具体是哪个模型、哪个目录，这里不写死**：它随机器和项目阶段漂（判官那一档两天里就换过一次），
钉在正文里就是把一个会漂的事实做成第二个真相源。**每轮开跑前问用户要「考生跑哪份配置」**，
拿到了再核开跑那行印出来的是不是它。

印出来的与用户说的对不上，或者跟上一轮不是同一个——**停下来问用户**，别闷头跑完：
那一轮跟历史轮次不可比，成本还可能高一个量级。

## 开跑前的三道闸（两条 loop 同一套）

每条用例开跑前逐条检查，**不过就挡住并记下理由**，不是跳过——跳过的话环境长期不通只表现为
「队列一直不消」，人得翻 loop 日志才知道为什么，而日志不在页面上。

| 闸 | 查什么 | 不过 → |
|---|---|---|
| MCP 通不通 | `initialize` + `tools/list` 一个来回 | 挡住·环境族（下轮探通自动回队列） |
| **工具集对不对** | `tools/list` 里**点名的工具在不在** | 挡住·环境族 |
| **代码同步** | 跑一次你给的同步命令 | 挡住·环境族 |
| 现场还在不在 | 行上的 `expires_at` 减安全余量 | 挡住·数据族（只能重新复现） |

### 工具集这道闸：名单已经内置，不用你配

`DBDOG_MCP_URL` 带着 toolsets / skillsets 查询串，**配歪了是静默的**：会话照起、跑批照跑，
只是手上少半套工具，然后报告写「查不到」。脚本里内置了这一轮必须拿得到的工具名单
（那是**我们自己声明的依赖**，不是会漂的环境值，所以钉得住），缺一个就挡。

要加别的：`export DBDOG_LOOP_EXPECT_TOOLS=<逗号分隔>`（给了就以它为准，不再用内置那份）。

### 代码同步这道闸：**它做不到热更新，它做的是「变了就停下」**

```bash
export DBDOG_LOOP_SYNC_CMD='claude plugin marketplace update dbdog-labs && claude plugin update dbdog-agent-obs'
```

（这条命令跑在 loop 自己的环境里，所以它同步的就是 `CLAUDE_CONFIG_DIR` 指的那一份。）

**没配就不挡**，只告警——为一个没配的变量让在跑的流水线全线停摆，比漏挡更坏。

**别指望它让新代码当场生效**：loop 进程启动时已经把脚本加载进内存，而判题包里那份 rubric
也是从**正在运行的那份脚本自己的目录**拷进去的。同步到新版本，本轮照样用旧脚本、旧口径，
`rubric_version` 也照样记旧的。

所以这道闸的实际作用是**发现版本变了就收尾停轮**：

- 判题：判完手上这一条就停，攥着的行照常放回队列；
- 诊断：守门跑在发题之前，所以整批放回、本轮一条都不跑。

两边都会印一行「插件已从 X 同步到 Y，**重启这条 loop** 就按新版跑」。
理由和这条 loop 一贯的纪律一致：宁可这一轮不跑，也不要跑出一批和新口径不可比、
外面却看不出差别的数据。

## 看输出

- `队列：待诊断 N 条 · 诊断中 M 条` —— 每轮都印。**M 长期不降说明有行卡住了**，
  多半是进程被杀，等租约回收（默认是 `--timeout-sec` 的两倍）。
- `本轮无事` —— 没有待诊断的复现。常态，不是错。
- `状态推进：X 条 → 待判题（其中 N 条跑完时已登记），Y 条没拿到 trace 已放回待诊断` —— Y 不为 0 要看一眼。
  括号里那个 N 是**正常的**：每条诊断一跑完，`run-experiment` 落实验事件时就当场把 trace
  写回诊断行、推到「待判题」了，收尾这一段只是兜底。N 长期为 0 反而要查——说明当场回填没打通。
  **一条每次都失败的用例会一直重试**，队列数字会暴露它。

跑完告诉用户：领了几条、几条出了 trace、队列里还剩多少待诊断与待判题。别复述整段日志。
